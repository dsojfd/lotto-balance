# 로또 밸런스 웹앱 설계

- 작성일: 2026-09-01
- 상태: 사용자 승인 완료
- 배포 대상: 공개 GitHub Pages PWA

## 1. 목적

직전 완료 추첨 회차까지의 공식 로또 6/45 당첨번호를 검증하여 분석하고, 사용자의 기기에서 안전한 난수로 추천 조합을 생성하는 공개 웹앱을 만든다. 링크로 누구나 사용할 수 있고, 홈 화면에 설치한 뒤에는 마지막 정상 데이터로 오프라인 실행할 수 있어야 한다.

이 앱은 과거 당첨번호가 미래 추첨을 예측한다고 주장하지 않는다. 로또 6/45의 각 고정 조합은 동일한 1등 확률을 가지며, 한 게임의 1등 확률은 1/8,145,060이다. 앱이 실질적으로 개선하는 부분은 여러 게임 내부의 완전 중복을 막고 조합 간 겹침을 줄여 구매 묶음의 범위를 넓히는 것, 그리고 사람들이 자주 고를 만한 형태를 피하는 선택지를 제공하는 것이다.

## 2. 범위와 비범위

### 초기 버전 범위

- 공개 링크로 사용하는 회원가입 없는 PWA
- GitHub Pages 정적 호스팅
- GitHub Actions를 통한 공식 당첨번호 자동 갱신
- 전체 회차 및 최근 10·30·50·100회 통계
- 균형·분산 추천과 완전 무작위 추천
- 1·5·10게임 생성, 기본값 5게임
- 기기 내 저장, 복사, 공유 및 새 당첨결과와 자동 대조
- 균형·분산 방식과 완전 무작위 방식의 과거 시점 백테스트
- 오프라인 실행과 마지막 정상 데이터 표시

### 초기 버전 비범위

- 회원가입, 사용자 계정, 클라우드 동기화
- 사용자 간 추천번호의 중앙 중복 방지
- 복권 구매 또는 결제 기능
- 푸시 알림
- 광고와 사용자 행동 추적
- 머신러닝 또는 AI를 이용한 당첨번호 예측
- 과거 통계로 당첨확률이 상승한다는 표현

## 3. 기술 구성

- 프런트엔드: React, TypeScript, Vite
- 설치·오프라인: Web App Manifest와 Service Worker를 사용하는 PWA
- 테스트: Vitest 기반 단위·속성 테스트와 Playwright 기반 브라우저 테스트
- 호스팅: GitHub Pages
- 자동화: GitHub Actions 예약 실행과 수동 실행
- 사용자 저장소: 브라우저 로컬 저장소

별도 상시 서버, 데이터베이스, 비밀 API 키는 사용하지 않는다.

## 4. 구성요소와 경계

### 4.1 공식 데이터 갱신기

GitHub Actions에서만 실행되는 독립 스크립트다. 동행복권 공식 결과 페이지에서 기존 최신 회차 다음 회차를 조회하고, 응답을 파싱한 뒤 스키마와 회차 연속성을 검증한다. 제3자 당첨번호 사이트는 데이터 원본이나 자동 대체 원본으로 사용하지 않는다.

검증이 성공하고 새 회차가 존재할 때만 공개 데이터 파일을 갱신한다. 새 결과가 아직 게시되지 않았거나 요청·파싱·검증이 실패하면 기존 정상 파일을 보존하고 작업을 실패 또는 정상 무변경으로 종료한다.

### 4.2 분석 엔진

당첨 회차 배열을 입력받아 통계 결과를 반환하는 순수 TypeScript 모듈이다. 네트워크, 화면, 저장소에 의존하지 않는다. 동일한 입력에는 동일한 결과를 반환한다.

### 4.3 번호 생성기

브라우저의 `crypto.getRandomValues()`를 난수 원천으로 사용한다. 화면이나 저장소와 분리된 도메인 모듈로 구현한다. 암호학적 난수를 사용할 수 없으면 `Math.random()`으로 몰래 대체하지 않고 사용자에게 오류를 표시한다.

### 4.4 백테스트 엔진

각 평가 회차 직전까지의 데이터만 분석 엔진에 전달한다. 미래 회차를 입력에서 구조적으로 제외하고, 균형·분산 방식과 완전 무작위 방식에 동일한 게임 수·평가 회차·반복 수를 적용한다.

### 4.5 PWA 화면

화면은 분석과 생성 결과를 표현하고 사용자 입력을 각 도메인 모듈에 전달한다. 추천 기록은 기기에만 저장한다. 앱 셸은 캐시 우선 갱신 방식, 최신 데이터 매니페스트는 네트워크 우선·캐시 대체 방식으로 불러온다.

## 5. 데이터 모델과 갱신 흐름

공개 당첨번호 데이터는 다음 의미를 보존한다.

- 스키마 버전
- 생성 시각
- 최신 정상 회차
- 원본 동행복권 URL
- 회차 번호
- 추첨일
- 오름차순 본번호 6개
- 보너스번호 1개

각 회차는 다음 조건을 모두 만족해야 한다.

- 회차 번호가 양의 정수이며 이전 회차와 연속됨
- 본번호가 1~45 범위의 서로 다른 정수 6개임
- 보너스번호가 1~45 범위이며 본번호와 겹치지 않음
- 본번호가 오름차순임
- 추첨일이 유효하고 회차 순서와 함께 증가함

자동화 흐름은 다음과 같다.

1. 토요일 추첨 종료 후와 일요일 오전에 예약 실행한다. 정각을 피하여 GitHub Actions 혼잡 가능성을 낮춘다.
2. 수동 실행도 항상 허용한다.
3. 기존 최신 회차의 다음 회차를 공식 결과 페이지에서 요청한다.
4. 결과 미게시 상태는 기존 데이터를 유지하는 무변경 결과로 처리한다.
5. 새 회차를 파싱하고 모든 검증을 수행한다.
6. 분석과 백테스트를 다시 계산한다.
7. 테스트와 정적 빌드가 모두 성공할 때만 데이터 변경을 커밋하고 같은 실행에서 Pages 산출물을 배포한다.
8. 어느 단계든 실패하면 기존 배포본은 유지한다.

공식 페이지의 URL이나 HTML 구조가 바뀌면 자동 추정으로 데이터를 채우지 않는다. 파서를 수정하고 공식 페이지와 대조한 테스트가 통과한 뒤 갱신을 재개한다.

## 6. 분석 설계

### 6.1 분석 창

사용자는 전체 회차와 최근 10·30·50·100회 창을 전환한다. 창마다 다음을 계산한다.

- 번호별 출현 횟수와 기대 출현 대비 편차
- 번호별 마지막 출현 이후 간격
- 홀수·짝수 개수 분포
- 1~22와 23~45의 저·고번호 개수 분포
- 1~10, 11~20, 21~30, 31~40, 41~45 구간 분포
- 여섯 번호의 합계와 전체 범위
- 인접 연속번호 개수
- 끝자리 중복 개수
- 이전 회차 본번호의 재출현 개수
- 번호 쌍 동시 출현 횟수

번호별 출현 횟수, 미출현 간격, 번호 쌍 통계는 화면에 정보로 제공하지만 다음 회차의 번호별 당첨 가능성으로 변환하지 않는다. 표본이 작은 최근 창과 번호 쌍 통계에는 표본 크기를 함께 표시한다.

### 6.2 균형·분산 추천

균형·분산 추천은 다음 절차를 따른다.

1. 1~45에서 서로 다른 숫자 6개인 후보 조합을 균등 난수로 만든다.
2. 과거 조합의 홀짝 수, 저·고번호 수, 합계, 범위, 구간 수, 연속번호 수, 끝자리 중복 수 분포를 이용해 조합 형태의 중심성을 계산한다.
3. 단일 번호의 최근 출현 횟수나 미출현 간격은 후보 번호의 당첨 가중치로 사용하지 않는다.
4. 과거에 드문 형태를 완전히 금지하지 않고 중심 형태를 약하게 우선한다.
5. 여러 게임을 선택할 때 이미 선택한 조합과 동일한 후보를 제외하고, 공통 번호 수가 적은 후보를 우선한다.
6. 완성된 각 게임은 오름차순으로 표시한다.

이 점수는 `당첨확률 점수`가 아니라 `조합 형태 점수`로 표기한다.

### 6.3 완전 무작위 추천

모든 6개 조합이 동일하게 선택될 수 있도록 1~45에서 균등 표본을 생성한다. 한 번에 생성한 묶음 안에서는 완전히 같은 조합만 제외하며, 조합 간 일부 번호 중복은 허용한다.

### 6.4 인기 선택 회피

사용자가 켤 수 있는 보조 선택지로 제공한다. 생일 범위인 1~31에 여섯 번호가 모두 몰린 조합, 여섯 개 완전 연속수, 동일 끝자리 과다와 같이 사람이 의도적으로 고를 가능성이 높은 형태를 약하게 낮춘다. 실제 판매 조합 데이터가 없으므로 상금 분할 가능성이 얼마나 감소하는지는 수치로 주장하지 않는다.

## 7. 백테스트 설계

- 최소 100회 학습 회차가 확보된 이후의 모든 평가 회차를 사용한다.
- 각 평가 회차에서는 그 직전 회차까지만 분석한다.
- 두 생성 방식에 같은 평가 회차, 게임 수와 반복 수를 사용한다.
- 재현용 백테스트 난수와 실제 사용자 추천용 암호학적 난수를 분리한다.
- 전체 평가 기간을 기본으로 표시하고 임의로 좋은 일부 기간만 기본 결과로 선택하지 않는다.
- 평균 일치 개수와 0~6개 일치 분포를 표시한다.
- 3·4·5·6개 일치 횟수와 불확실성 구간을 표시한다.
- 결과 차이가 반복 표본의 변동 범위 안이면 `무작위 대비 우위 확인 안 됨`으로 표시한다.
- 결과가 우수해 보여도 미래 당첨확률 상승으로 표현하지 않는다.

## 8. 화면 설계

사용자가 승인한 홈 화면은 `A. 바로 추천` 방식이다. 하단 메뉴는 추천·분석·검증·저장의 네 영역으로 구성한다.

### 8.1 추천

- 앱 이름 `로또 밸런스`
- 최신 정상 회차와 갱신 시각
- 균형·분산 추천과 완전 무작위 전환
- 1·5·10게임 선택, 기본 5게임
- 추천번호 생성 버튼
- 각 조합의 홀짝, 합계, 연속수와 형태 설명
- 전체 저장, 복사, 시스템 공유, 다시 생성
- 추천 기준 상세 설명

사용자가 버튼을 누를 때마다 새 난수를 사용한다. 서로 다른 사용자와 서로 다른 실행의 결과는 일반적으로 다르지만, 서버가 사용자 간 결과를 조정하지 않으므로 우연한 동일 조합 가능성은 남는다.

### 8.2 분석

- 분석 창 전환
- 번호별 출현과 미출현 간격
- 홀짝·구간·합계·연속번호 분포
- 번호 쌍 동시 출현 통계
- 통계가 예측이 아니라는 상시 안내

### 8.3 검증

- 두 생성 방식의 동일 조건 비교
- 사용한 기간, 게임 수, 반복 수와 난수 재현 정보
- 평균 일치 수와 등급별 일치 횟수
- 무작위 대비 차이에 대한 제한적 결론

### 8.4 저장

- 대상 회차별 추천 묶음 저장
- 새 결과 갱신 후 자동 대조
- 본번호 및 보너스 일치에 따른 예상 등수 표시
- 저장·삭제·복사·공유
- 모든 기록이 현재 기기에만 있다는 안내

## 9. 오프라인과 로컬 저장

- 앱 셸과 마지막 정상 공개 데이터는 Service Worker 캐시에 저장한다.
- 온라인에서는 최신 데이터 매니페스트를 먼저 확인하고, 실패하면 캐시를 사용한다.
- 오프라인일 때 `오프라인 · 제N회 저장 데이터 사용 중`과 마지막 갱신 시각을 표시한다.
- 생성, 분석, 저장 기록 열람은 오프라인에서도 동작한다.
- 저장 데이터에는 스키마 버전을 포함하고 명시적인 마이그레이션만 수행한다.
- 손상된 로컬 기록은 공개 당첨번호 데이터와 분리하여 처리하며, 공개 데이터까지 삭제하지 않는다.

## 10. 오류 처리

- 공식 데이터 요청 실패: 기존 정상 데이터 유지
- 새 회차 미게시: 무변경 처리 후 다음 예약에서 재시도
- 회차·날짜·번호 검증 실패: 빌드와 배포 중단
- 공식 HTML 구조 변경: 파싱 실패 후 수동 수정 필요 상태 기록
- 최신 매니페스트 요청 실패: 캐시된 정상 데이터 사용
- 공개 데이터 스키마 불일치: 신규 데이터 거부
- 암호학적 난수 사용 불가: 추천 생성 중단과 명확한 오류 표시
- 브라우저 저장 실패: 화면 결과는 유지하고 저장 실패만 안내
- Web Share API 미지원: 텍스트 복사 방식 제공

사용자가 확인하지 못한 상태에서 기존 정상 데이터, 저장 추천번호 또는 설정을 자동 삭제하지 않는다.

## 11. 검증 계획

### 단위·속성 테스트

- 회차 데이터 스키마와 연속성
- 번호 범위, 정수성, 본번호·보너스 중복
- 모든 분석 지표의 고정 예제
- 생성 조합의 6개 고유 번호와 정렬
- 생성 묶음 내부의 동일 조합 부재
- 미래 회차가 백테스트 입력에 포함되지 않음
- 동일 백테스트 시드의 결과 재현
- 로컬 저장 스키마와 마이그레이션

### 통합 테스트

- 저장된 공식 페이지 샘플의 파싱
- 새 회차 추가와 무변경 처리
- 잘못된 공식 응답에서 기존 데이터 보존
- 데이터 갱신부터 분석·빌드까지의 전체 작업

### 브라우저 테스트

- 320px 이상 모바일과 일반 PC 폭의 반응형 화면
- 추천 생성, 저장, 삭제, 복사와 공유 대체 동작
- 새 당첨결과와 저장 번호 대조
- 온라인 최신 데이터와 오프라인 캐시 전환
- 키보드 조작, 명확한 레이블과 기본 접근성 검사

### 배포 게이트

데이터 검증, 단위·통합·브라우저 테스트, 정적 빌드가 모두 성공해야 GitHub Pages를 갱신한다. 실패한 자동 작업은 기존 Pages 배포를 변경하지 않는다.

## 12. 완료 기준

- 직전 완료 회차까지의 공식 데이터만 분석한다.
- 잘못된 새 데이터가 기존 정상 데이터를 덮어쓰지 않는다.
- 1·5·10게임을 두 생성 방식으로 만들 수 있다.
- 한 생성 묶음 안에 동일 조합이 없다.
- 균형·분산 추천의 형태 점수와 당첨확률을 구분한다.
- 분석과 백테스트가 미래 회차를 사용하지 않는다.
- 인터넷 없이 마지막 정상 데이터로 생성·분석·저장 열람이 가능하다.
- 저장 추천번호를 새 당첨결과와 정확히 대조한다.
- 공개 GitHub Pages 링크와 홈 화면 설치가 동작한다.
- 모바일 320px 폭부터 PC 화면까지 주요 조작이 겹치거나 잘리지 않는다.
